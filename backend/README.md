# Backend: архитектура и правила

Документ описывает, как устроен бэкенд Gressus и как писать новый код так, чтобы каждый модуль работал с чёткими слоями.

---

## Где что лежит

- **Модули** — `backend/modules/<module_name>/` (например `patients`, `sessions`, `runtime`, `insole`, `health`).
- **Общая инфраструктура** — `backend/core/` (конфиг, БД), `backend/common/` (общие `Depends`).
- **Состояние приложения** — `backend/app_state/` (инициализация БД, runtime manager).
- **Точка входа** — `backend/main.py`, lifespan — `backend/lifespan.py`.
- **Роутеры** подключаются в `backend/routers.py` (список `routers`), регистрация — в `lifespan`.
- **Миграции** — `backend/migrations/` (Alembic).

Uvicorn запускается из корня репозитория:

```bash
uvicorn backend.main:app --host 0.0.0.0 --port 8000
```

В Docker рабочая директория — `/gressus`, `PYTHONPATH` указывает на корень проекта.

---

## Про окружение и авторизацию

Gressus обычно разворачивается в **локальном контуре** рядом с экзоскелетом (одна машина/локальная сеть, без публичного доступа). Поэтому **авторизации как таковой сейчас нет и не планируется (пока)**. Если в будущем появится удалённый доступ или мультипользовательский режим — добавим auth и вынесем проверки в `policy.py`.

## Модуль = bounded context

Каждый модуль — отдельный кусок продукта со своими:

- **API** (HTTP-эндпоинты)
- **Бизнес-логикой** (сервис)
- **Доступом к данным** (репозиторий — если модуль ходит в БД)
- **Схемами запросов/ответов** (DTO)
- **Зависимостями** (инжект сессии, конфига, сервиса)

Модули не лезут в репозитории и сервисы друг друга. Общие вещи (ORM-модели, DTO) импортируются по явному контракту — например, `sessions` проверяет существование пациента через `Patient` из `patients.models`, без вызова `PatientRepository`.

Не все модули обязаны иметь полный набор слоёв (например `runtime` и `insole` работают без БД).

## Слои внутри модуля

Рекомендуемая структура файлов и ответственность:

| Слой            | Файл              | Ответственность |
|-----------------|-------------------|-----------------|
| **API**         | `api.py`          | Роутер FastAPI, валидация входа (тело/query), вызов сервиса, возврат ответа. Никакой бизнес-логики и SQL. |
| **Сервис**      | `service.py`      | Сценарии использования, валидация доменных правил, оркестрация репозиториев и внешних вызовов. Не знает про HTTP. |
| **Репозиторий** | `repository.py`   | Работа с БД: выборки, вставки, обновления. Только SQLAlchemy 2.0, без кастомных QueryBuilder. |
| **Схемы**       | `schemas.py`      | Pydantic-модели: DTO создания/обновления, ответы, фильтры. |
| **Зависимости** | `dependencies.py` | FastAPI `Depends`: сессия БД, инстанс сервиса. |
| **Модели**      | `models.py`       | SQLAlchemy ORM (только у модулей с БД). |

Дополнительно по необходимости:

- `policy.py` — проверки прав (если появится авторизация).
- `interfaces.py` — абстракции для подмены в тестах.

Поток данных: **API → Service → Repository → DB** (или **API → Service → внешний HTTP**, как в `runtime`).

Зависимости инжектятся в API; сервис создаёт репозиторий в конструкторе, получая `AsyncSession` из `get_db_session`.

## Правила

1. **Нет SQL в зависимостях**  
   В `dependencies.py` — только получение сессии, конфига, создание сервиса. Загрузка сущностей по id и валидация — в сервисе (или в репозитории по вызову из сервиса).

2. **Доменные проверки в сервисе**  
   «Пациент не найден», «нельзя обновить архивного», «автоматически проставить `ended_at` при завершении сессии» — в `service.py`, не в `api.py`. Когда появится авторизация, проверки прав — тоже в сервисе (или в `policy.py`).

3. **Репозиторий — только данные**  
   Нативный SQLAlchemy 2.0: `select()`, `where()`, `options(selectinload(...))`, `execute()`, `scalars().first()` / `scalars().all()`, `add` / `flush` / `refresh`. Без обёрток типа QueryBuilder.

4. **Транзакции: в репозитории не коммитим**  
   Граница транзакции — в `get_db_session` (`backend/core/database/manager.py`): по завершении запроса один `commit` (или `rollback` при ошибке). В репозитории только `add()` / `flush()` / `refresh()`. Коммит в репо не вызываем.

5. **Модули не зависят от HTTP друг друга**  
   Общая логика — через сервисы, репозитории или общие схемы/модели, а не через внутренние HTTP-вызовы между модулями. Внешние системы (ROS `session_manager`) — только из своего модуля (`runtime`).

6. **При ответе не мутировать загруженные ORM-объекты**  
   Сессия по запросу в конце делает `commit`. Для ответа строить DTO (`PatientRead.model_validate(entity)`), менять **DTO**, а не entity. Изменения ORM — только в сценариях явного обновления (с последующим `flush` в репо).

## Как добавить новый модуль

1. Создать папку `backend/modules/<name>/`.
2. Добавить нужные файлы:
   - `api.py` — роутер и эндпоинты;
   - `service.py` — сценарии;
   - `repository.py`, `models.py` — если модуль пишет в БД;
   - `schemas.py` — DTO;
   - `dependencies.py` — `Depends` для сервиса.
3. В `api.py` инжектить сервис через `dependencies`, в хендлерах вызывать только методы сервиса.
4. Подключить роутер в `backend/routers.py` в список `routers`.
5. Если нужна новая таблица — добавить модель и миграцию Alembic в `backend/migrations/versions/`.

Пример минимального потока: запрос → `api` (Depends) → `service.method()` → `repository` → БД → DTO в ответ.

## Примеры эталонных модулей

По слоям с БД ориентироваться на:

- `backend/modules/patients` — CRUD, soft-delete через `archived_at`;
- `backend/modules/sessions` — вложенные маршруты под пациента, авто-нумерация сеансов.

Без БД, с внешним вызовом:

- `backend/modules/runtime` — `SessionManagerClient` + `RuntimeService` → HTTP `:9090` (stack lifecycle, P.GEAR commands).
